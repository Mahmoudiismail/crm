# Detailed Execution Plan: Fix 5 Critical Runner/Tasker Blockers

## Overview
This plan outlines the minimal, robust architectural fixes for the 5 critical Runner and Tasker blockers specified in the issue.

---

## 1. Blocker 1 — Periodization and Date Ownership in `ExternalApp`
### Problem
`RunnerTask` currently owns `period_mode`, `start_date`, and `end_date`, whereas periodization and date configuration must belong to `ExternalAppSpec`.

### Architectural Changes
- Update `ExternalAppSpec` in `src/runner/config/models.rs`:
  ```rust
  pub struct ExternalAppSpec {
      pub app_id: String,
      #[serde(default)]
      pub args: std::collections::HashMap<String, String>,
      #[serde(default)]
      pub period_mode: PeriodMode,
      #[serde(default, skip_serializing_if = "Option::is_none")]
      pub start_date: Option<String>,
      #[serde(default, skip_serializing_if = "Option::is_none")]
      pub end_date: Option<String>,
  }
  ```
- Remove `period_mode`, `start_date`, and `end_date` from `RunnerTask`.
- In `src/runner/config/migration.rs`:
  - Update `RunnerTaskLegacy` to read legacy task-level `period_mode`, `start_date`, `end_date`.
  - In `From<RunnerTaskLegacy> for RunnerTask`, iterate over all `TaskStep`s (in both `steps` and `post_run_steps`). For every `ActionSpec::ExternalApp(ref mut spec)`, migrate the legacy task-level values into `spec` IF `spec` does not already have an explicit period/date setting.
- In `src/runner/engine/pipeline.rs` and execution dispatcher:
  - Update `run_external_app` and pipeline step execution to use the `period_mode`, `start_date`, `end_date` directly from `ExternalAppSpec`.
- In `src/runner/gui/templates.rs`, `src/runner/gui/forms.rs`, and `src/runner/assets/js/forms.js`:
  - Move periodization / date UI controls out of the top-level task form and place them inside each `ExternalApp` action card/form section.

## 2. Blocker 2 — ExternalApp-Specific Execution Preview
### Problem
Live Execution Preview was previously task-level and received a whole `RunnerTask`, duplicating or misaligning preview logic.

### Architectural Changes
- Modify the preview endpoint (`/api/tasks/preview` or adapter) to accept an `ExternalApp` action configuration alongside task schedule & working hours context.
- Use the **EXACT SAME** `generate_upcoming_executions` and `generate_execution_periods` backend resolution logic that actual execution uses.
- Ensure date semantics strictly follow:
  - Start is resolved first.
  - End is resolved relative to the resolved Start as the base date.
  - Return maximum 10 upcoming execution periods.
  - Return empty array ("No upcoming executions") if none exist or schedule is empty.
  - Fail explicitly on invalid date expressions.
- Render the preview table/section inside each `ExternalApp` action card in the GUI task editor. Remove any task-level preview UI.

## 3. Blocker 3 — Tasker Script Hash without Runtime Data
### Problem
`ScriptManager` computes SHA-256 hashes on PowerShell script strings containing embedded runtime values (e.g. email addresses, output paths). Any runtime value change produced a new timestamped script file.

### Architectural Changes
- Separate static script template logic from runtime parameter bindings:
  - Static `.ps1` files generated by Tasker modules (`department_split.rs`, `outlook.rs`, `dashboard_updater.rs`, `crm_open_sohail/powershell.rs`, `opd_task/powershell_email.rs`) will define standard PowerShell `param(...)` blocks at top of script.
  - Runtime values will be passed as named CLI arguments (e.g., `-Email "..." -Subject "..." -OutputDir "..."`) when invoking `powershell.exe`.
- Ensure `ScriptManager.get_or_create_script` is invoked with the **STATIC TEMPLATE ONLY** (which contains `param(...)` headers but no interpolated runtime variables).
- Hashing static templates ensures:
  - Changing runtime values (emails, paths) reuses the existing active `.ps1` without creating new timestamped files.
  - Changing actual Rust-generated script logic creates a new timestamped version.
  - User manual edits to active `.ps1` files are strictly preserved when generator static template hash is unchanged.

## 4. Blocker 4 — Process Timeout Process Tree Termination
### Problem
`tokio::time::timeout` around `cmd.output()` timed out in Rust but left child processes (e.g. `powershell.exe`, `excel.exe`, `crm.exe`) running as orphans.

### Architectural Changes
- In `src/runner/engine/process.rs`:
  - Spawn child using `let mut child = ctx.cmd.spawn()?;` and obtain stdout/stderr handles or use Tokio child process management.
  - Wrap wait/output in `tokio::time::timeout(...)`.
  - On timeout:
    - Execute process tree kill (`child.kill().await` and on Windows execute `taskkill /F /T /PID <pid>`) to reliably terminate child and all descendants (Excel, PowerShell, CRM, etc.).
    - Wait for process termination and cleanup handles.
    - Return a explicit timeout error (`Command timed out after Ns`).
  - Preserve stdout and stderr capture from pipes.

## 5. Blocker 5 — Runner GUI HTTP Security

### 5A — GET Mutation Prohibition
- Audit all routes in `src/runner/gui/routes.rs`:
  - Ensure `/create`, `/update`, `/delete`, `/run` (and any other state-changing endpoints) strictly reject `GET` requests with `HTTP 405 Method Not Allowed`.
  - Accept state changes ONLY on `POST` requests.
  - Update all forms in `templates.rs` and JavaScript `fetch` calls in `src/runner/assets/js/` to use `POST`.

### 5B — Non-Loopback Binding Security (Option B)
- In `src/runner/config/validation.rs` or startup initialization (`src/bin/runner.rs` / `src/runner/gui/mod.rs`):
  - Parse `gui_host`.
  - Check if `gui_host` is non-loopback (i.e. not `127.0.0.1`, `localhost`, `::1`, `[::1]`).
  - If `gui_host` is non-loopback AND no explicit auth mechanism/token configuration is enabled, fail startup immediately with a clear security error message refusing to bind to non-loopback interfaces without protection.
  - Localhost loopback remains easy to use without configuration.

## Testing Strategy & Coverage
Add/update deterministic tests covering:
1. `ExternalAppSpec` period/date configuration ownership & legacy migration.
2. Fixed/Dynamic date resolution in `ExternalApp`.
3. `ExternalApp`-specific execution preview max 10 future executions using shared backend execution generator.
4. Same Start/End "next weekday" semantics (e.g. `next sat` -> same date for Start and End).
5. Invalid date expression error handling (no silent fallbacks).
6. ScriptManager hash invariance when Tasker runtime arguments change.
7. ScriptManager versioning on static script template logic changes.
8. Preservation of user-edited active scripts.
9. Process timeout process tree termination test.
10. HTTP GET mutation rejection (405 Method Not Allowed).
11. Startup rejection on unauthenticated non-loopback `gui_host`.

- No SPA/build tooling or external workflow engine will be added.
- Generated `TaskStep`s will not be persisted.
